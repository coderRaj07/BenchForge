# orders-mixed dataset

`dataset.profile: orders-mixed` is the only profile in version 0.1.0. `seed.Build` generates it in memory. `seed.Apply` loads it with `COPY` after migrations have created the tables.

## Cardinality

Scale `1` is the reference size.

| Table | Rows at scale 1 | Formula |
| --- | --- | --- |
| `customers` | 1,000 | `round(1000 * scale)`, at least 1 |
| `products` | 200 | `round(200 * scale)`, at least 1 |
| `orders` | 10,000 | `round(10000 * scale)`, at least 1 |
| `order_items` | about 2 per order | 1, 2, or 3 lines, chosen from the seeded RNG |

Scale `2` is what the integration test uses for the regression pair: 2,000 customers, 400 products, 20,000 orders.

Ids are `1..n` on every table. `maxFrom: customers` therefore means `random` from `min` through the customer count.

## Determinism

The generator is `math/rand/v2` PCG seeded with `dataset.seed` and a fixed stream constant. Customer names cycle through a fixed list. Emails are `customer<id>@example.test`. Product prices are `100 + rng` cents, up to 20,000. Each order picks a customer uniformly, then one to three items. Line quantity is 1 to 3. `orders.total_cents` is the sum of `qty * price_cents`. `created_at` is a deterministic offset from `2024-01-01T00:00:00Z`, not the wall clock. Status is `created`.

`Data.Checksum` covers the counts and the first and last order. `Data.Invariants` checks ranges and totals before anything is sent to the database. After `COPY`, the database checks the same total with SQL and returns an error if any order disagrees. `ANALYZE` runs on all four tables so the planner sees the scale you asked for.

Two builds with the same seed and scale match. A different seed changes the checksum. Tests cover both.

## Schema

`workloads/postgres/migrations/001_orders.sql` is the reviewed schema:

- `customers(id, email, name)`
- `products(id, sku, price_cents)` with `price_cents > 0`
- `orders(id, customer_id, total_cents, status, created_at)` with status restricted to `created`, `paid`, or `cancelled`
- `orders_customer_created_idx` on `(customer_id, created_at DESC)`
- `order_items(id, order_id, product_id, qty, price_cents)`
- `order_items_order_idx` on `(order_id)`

Identity columns are `GENERATED BY DEFAULT AS IDENTITY` so the loader can supply ids and then `setval` the sequences to `MAX(id)`.

## Refusing to overwrite

`seed.Apply` counts `customers` first. If the count is not zero, it returns an error and does not truncate. An ephemeral container is empty. An external database that already has data is left alone.

## Queries shipped with the dataset

| File | Id | Plan shape |
| --- | --- | --- |
| `workloads/postgres/sql/get_customer_orders.sql` | `get-customer-orders` | Equality on `customer_id`, intended to use the index |
| `workloads/postgres/sql/get_customer_orders_seqscan.sql` | `get-customer-orders` | `(customer_id + 0) = $1`, which does not match the index |
| `workloads/postgres/sql/create_order.sql` | `create-order` | Insert of one order, `RETURNING id` |

The regression manifest keeps the query id, seed, scale, concurrency, and name of the indexed manifest, and changes only the SQL file. Comparison is by query id. The report records both SQL fingerprints and adds an informational finding when they differ.

`create_order` during a measured run inserts extra rows. Repeats are not bit-identical once that statement is in the mix. The select-only manifests avoid that. The integration test uses the select-only pair.
